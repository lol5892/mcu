# Развёртывание и администрирование закрытой беты

## Разделение сред

Исходная main и Pages остаются на 2.5.3. Бета — отдельный checkout `/workspace/kino-vdvoem-beta`, отдельный Sites project и отдельный Supabase `aadztcqfwtuniucrlsgc`. Миграции и функции никогда не отправляются в исходный Supabase. CI-ветка `public-beta-3` не предназначена для слияния в main; Pages workflow удалён только в этой ветке. Создание отдельного GitHub-репозитория текущей интеграцией запрещено; окончательный перенос исходников в новый репозиторий выполняется после предоставления владельцем такого репозитория. Закрытый Sites получает свою независимую копию исходников.

Развёртывание новой базы: только пустой отдельный проект, затем все `supabase/migrations` по порядку и `supabase/public-migrations` по порядку. Каталог обновляется `node scripts/catalog-sql.mjs`. Первая публичная миграция останавливается, если уже есть семья или исходный bootstrap. Новые миграции создаются штатным Supabase CLI; история hosted MCP может иметь фактические временные отметки применения, поэтому сверяются также имена и контрольные суммы. Не применять повторно начальную public_beta к заполненной базе.

Для статической оболочки нужны только URL и publishable key нового проекта, VAPID public key при подключении push. Service-role, CRON_SECRET, VAPID private key, пароль базы и SMTP никогда не включаются в браузерный комплект. `verify:beta` блокирует наследование старого конфигурационного файла и запрещённого backend URL. Приём денег выключен, регистрация выключена.

## Настройка SMTP — владельцу

Встроенная почта Supabase предназначена для команды/демо и не является готовой отправкой обычным пользователям. См. [официальные ограничения и настройку SMTP](https://supabase.com/docs/guides/auth/auth-smtp). Подтверждение email не отключать.

1. После решения вопроса локализации выбрать почтового провайдера, разрешающего ваш статус и страну. Для российского размещения изучить российского транзакционного провайдера, например [Yandex Cloud Postbox](https://yandex.cloud/ru/docs/postbox/); возможность подключения и актуальную цену подтвердить в его кабинете. Наличие бесплатного тарифа за владельца не предполагается.
2. Зарегистрировать домен отправителя, подтвердить его, настроить SPF/DKIM и DMARC по инструкциям провайдера. Пароли SMTP передавать только в защищённые настройки сервера, не в чат, GitHub или VITE_*.
3. В Auth → SMTP указать host, port, login, password, From и имя «Кино вдвоём». Настроить Site URL и точный allowlist redirect URL нового staging. Старый URL приложения не менять.
4. Email confirmation оставить включённым. Для открываемого набора включить встроенные лимиты Auth и CAPTCHA/Turnstile с проверенной серверной верификацией, если выбранная конфигурация это требует. Для закрытой беты действует серверный whitelist.
5. На собственных/согласованных тестовых адресах обычных провайдеров проверить регистрацию, вход, код/ссылку, истечение, повтор и восстановление. Проверить спам, возвраты, время доставки и ошибочный код. Зафиксировать дату и результаты; администраторское email_confirm=true в QA доставку не доказывает.
6. Только после юридического решения, проверки почты и прав добавить разрешённые адреса создателей, открыть accepting_families до лимита 10–20 и выпустить сборку с разрешённым входом. Сейчас эти шаги не выполнены и набор закрыт.

Допуск создателя делается администратором в `mv_private.beta_enrollments` с ограниченным expires_at. Приглашённый второй адрес допускается только на время действительного приглашения. Не публиковать общую административную кнопку или SQL-пример с настоящими email. Создание нового пространства при заполненном лимите прекращается атомарно.

## Собственный Cloudflare

Аккаунта Cloudflare у владельца пока нет. После регистрации: создать Pages/Workers Static Assets проект из отдельного репозитория, `npm ci` → `npm run build:beta`, выход `dist`, HTTPS, root base `./`. Для технического staging сохранить VITE_BETA_AUTH_READY=false. При необходимости подключить собственный домен; *.pages.dev позволяет обойтись без покупки домена. Для закрытого теста настроить Cloudflare Access, не считать секретный URL защитой.

Добавить только новый origin в APP_ORIGINS Edge-функций и точный redirect URL Auth. Проверить доступность через реальные российские сети, manifest, scope нового домена, установку на iPhone, офлайн и безопасное обновление. Перенос публичного адреса между доменами не переносит установленную PWA автоматически: выбрать окончательный адрес до реальных приглашений. Исходная семейная PWA продолжает жить по прежнему адресу.

## Edge, Storage и Push

`media-upload` и `push-dispatch` используют свою серверную авторизацию. `verify_jwt=false` не даёт открытого доступа: фото проверяет auth.getUser и членство, отправитель push — секретный Bearer. VAPID-ключи у нового проекта отдельные; подписки исходной семьи не переносятся. CRON_SECRET, VAPID private и контакт VAPID хранятся в Vault/Edge secrets. APP_ORIGINS должен совпасть с новым origin; localhost — только локальная разработка.

Включение уведомлений — только по осознанному нажатию пользователя. Реальные Apple Push и физические iPhone требуют ручной проверки. Сохранение задания и принятие его push-сервисом не означают фактический показ на телефоне.

На техническом стенде планировщик пока не включается. До реального закрытого теста настроить минутный cron для напоминаний и ретраев через проверенный серверный секрет, проверить quiet hours, lease и идемпотентный ACK. Не добавлять cron, искусственно обходящий ограничения неактивности Free-проекта. Временный hosted QA-инструмент после проверки заменяется ответом 404, его секрет ротируется; это не административный API продукта.

## Административный контроль

Только доверенный администратор выполняет `select mv_private.beta_admin_report();`. Отчёт содержит число пар/аккаунтов, байты базы и файлов, очередь/ошибки push, число пишущих аккаунтов за 7 дней, запросы удаления и предупреждения бюджета. В нём нет текстов впечатлений, email, имён и изображений. Трафик и пик Realtime намеренно null: достоверные значения берутся в Supabase Usage, а не выдумываются SQL-функцией.

Предупреждения при 70% DB/Storage и заполнении лимита видны в отчёте. При 85% провайдерской квоты оператор закрывает accepting_families и оценивает расходы; существующие пары не удаляются. Настроить собственные предупреждения расхода в Dashboard до реального набора. Связь владельца: https://t.me/lol5892. Автоматические сообщения владельцу из этой разработки не отправлялись.

Запросы удаления обрабатывать по утверждённой процедуре и срокам. Проверить личность, запрос второго участника при удалении общей истории, выгрузку, отозвать refresh-сессии, учесть ещё живые JWT, обработать все FK, Storage и push. Не исполнять непроверенный CASCADE по family_id. Новый партнёр в старую историю не подселяется. До согласования процедуры реальные пары не регистрируются.

## Резервное копирование и восстановление

Free не включает гарантированную автоматическую резервную копию. До реальных данных нужны зашифрованный ежедневный pg_dump, отдельная копия файлов Storage, контроль выполнения и ротация с согласованным сроком. Использовать PGHOST/PGUSER/PGPASSWORD через закрытые переменные процесса или libpq service file с правами 0600; не передавать пароль в строке команды и не класть его в репозиторий. Хранилище резервных копий должно соответствовать выбранной юрисдикции.

Проверка восстановления выполняется в новой изолированной базе: pg_restore, сравнение количества/идентификаторов/дат наград, XP, членства и RLS; отдельно восстановление Storage и приватного доступа. Новый namespace/ключи Auth требуют отдельного плана переноса идентичности, нельзя обещать сохранение старых JWT при произвольной замене проекта. Исходная семейная база не используется как полигон.

Локальный нагрузочный стенд: `python3 scripts/load-public-beta.py`. Он создаёт только `kino_load_test` в выделенном контейнере, 200 искусственных SQL-идентичностей, а не сотни hosted Auth-аккаунтов. Эти результаты не заменяют тест 200 WebSocket-соединений через интернет.
